## 1. Ручной чек-лист в Telegram

Автотесты зелёные, но поведение в реальном клиенте ещё не проверялось.

1. `/start` → снизу дефолтные кнопки; inline-меню не сломано.
2. Админ: «➕ Слот» → ввести занятое время → ошибка сразу, с временем и форматом
   конфликта; кнопок «Онлайн/Офлайн» нет; ввести свободное → кнопки формата;
   создать слот → успех.
3. Ученик: слоты → пагинация → выбрать слот → предмет → запись. Проверить, что
   после каждого шага активна только одна клавиатура.
4. Мои записи → отмена → подтверждение → результат; старые кнопки не работают.
5. Намеренно отправить неверное имя/класс/ID 2–3 раза — не должно появляться
   несколько сообщений с кнопками.
6. Нажать старую кнопку из истории (если осталась) — «Кнопка устарела», без
   побочных действий.
7. Админ: ученик создаёт запись → приходит уведомление с кнопками → нажать
   «Запись #N» → карточка внизу, отметить посещаемость.
8. Админ в середине ввода времени слота → приходит уведомление → нажать кнопку
   уведомления → вежливый отказ, сценарий не сброшен.
9. Перезапустить бота посреди сценария → нажать «✖️ Отмена» → состояние
   сброшено, дефолтные кнопки вернулись.
10. `/help`, `/start`, `/cancel` работают в любом состоянии.

## 3. Риски и ограничения

- Telegram не даёт редактировать сообщения старше ~48 часов; снятие клавиатуры и
  `edit_text` — best-effort, ошибки не должны ломать сценарий.
- Сообщения с медиа нельзя `edit_text`; текущие экраны текстовые, но хелпер
  должен корректно падать в «отправить новое».
- Реестр экранов в памяти: после рестарта пуст. Политика «пусто = разрешаем»
  обязательна.
- Постоянная reply-клавиатура «липкая»: после рестарта посреди сценария у
  пользователя может остаться «✖️ Отмена». Обработчик отмены и `/start` должны
  всегда восстанавливать дефолт.
- При двух быстрых нажатиях возможна гонка реестра; в v1 достаточно принимать
  последний рендер, при необходимости — дедупликация по `callback.id`.
- Не забывать `callback.answer()` во всех ветках, включая отказы middleware,
  иначе кнопка «крутится».

### 4.4. Как диагностировать, если повторится

Логи бота теперь можно писать в файл (каталог `logs/` исключён из git,
файл `logs/bot.log` создан):

```powershell
cd telegram-bot
..\.venv\Scripts\python.exe -m tgbot *>&1 | Tee-Object -FilePath ..\logs\bot.log -Append
```

Если в файле «кракозябры» — запускать в PowerShell 7 (`pwsh`) или добавить
`-Encoding utf8`.

Что смотреть в первую очередь:

```powershell
Select-String -Path ..\logs\bot.log -Pattern "query is too old|Отклонена устаревшая|TelegramNetworkError|Не удалось проверить время|Сначала завершите"
```

- `Отклонена устаревшая кнопка 'slotfmt:...'` → сработал stale-guard, кнопка
  формата была отрезана (п. 2–3).
- `Сначала завершите действие` → залипший FSM (п. 6).
- `Не удалось проверить время` → в логе бэкенда должен быть
  `GET /slots/overlap`; если его нет — бот не дошёл до вызова.
- `query is too old` → `answer()` пришёл слишком поздно (п. 1).

Свободная память перед запуском (меньше ~0,5 ГБ — сначала освободить):

```powershell
$os = Get-CimInstance Win32_OperatingSystem
"FreeRAM_GB={0:N2}" -f ($os.FreePhysicalMemory/1MB)
```

7. **Аудит и лимиты.** Журнал попыток привязки, ограничение частоты попыток

### 5.5. Критерии готовности

- Ни один пользователь не может привязать `student_id` без подтверждения
  преподавателем или одноразового кода.
- Повторная привязка уже занятого `student_id` отклоняется и логируется.
- `ADMIN_IDS` не может регистрироваться, привязываться и бронировать; в меню
  админа нет ученических кнопок.
- Преподаватель не может забронировать созданный им слот (после появления
  владельца слота).
- Отмена и посещаемость доступны только владельцу брони или админу.
- `admin-list`, создание слотов и админские операции требуют ключа; бэкенд не
  слушает внешние интерфейсы.
- Есть тесты на отказы: чужой `/link`, повторная привязка, бронь админом,
  отмена чужой брони.
